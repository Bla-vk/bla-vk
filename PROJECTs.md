### 1. AWS Dev Environment with Terraform
**Repo:** [link](https://github.com/Bla-vk/terraform-aws-dev-environment)

![Terraform checks](https://github.com/Bla-vk/terraform-aws-dev-environment/actions/workflows/terraform.yml/badge.svg)

Infrastructure as Code project that builds a complete development environment on AWS with one `terraform apply`: a custom VPC (`10.100.0.0/16`), a public subnet, a private subnet that reaches the internet only through a NAT gateway, a security group, an SSH key pair and an Ubuntu 24.04 EC2 instance. The code is split into reusable `network` and `compute` modules, and the AMI is found with a data source rather than hardcoded.

Terraform state lives in an encrypted, versioned S3 bucket with native state locking, so two runs cannot change it at once. The security group allows SSH and HTTP only from my current public IP, which an `http` data source looks up on every run. A `user_data` script installs Docker Engine on first boot and starts an nginx container, and a `local-exec` provisioner adds the new server to my SSH config. I proved the NAT design by connecting to a test server in the private subnet through the public server and checking that its outbound IP matched the NAT gateway's Elastic IP.

A GitHub Actions workflow runs `terraform fmt -check`, `init -backend=false` and `validate` on every push, and I documented a deliberate failing run (a formatting error) followed by the fix. The environment is destroyed after each test, because the NAT gateway bills by the hour. The README covers the troubleshooting, including a failed boot script and a stale SSH entry.

**Skills demonstrated:** Terraform, Infrastructure as Code, Terraform modules, S3 remote state and locking, Amazon VPC, NAT gateway, security groups, EC2, data sources, `user_data` and cloud-init troubleshooting, Docker, GitHub Actions CI, cost control, `.gitignore` hygiene for state and secrets

### 2. Django API on AWS ECS Fargate (Terraform, with CI/CD)
**Repo:** [link](https://github.com/Bla-vk/Simple-CRUD-API) (see the `terraform` folder)

[![CI](https://github.com/Bla-vk/Simple-CRUD-API/actions/workflows/ci.yml/badge.svg)](https://github.com/Bla-vk/Simple-CRUD-API/actions/workflows/ci.yml)

Deployed my Django REST API to Amazon ECS Fargate behind an Application Load Balancer, with the whole stack defined in Terraform: a VPC with two public subnets in two availability zones, an ECR repository (immutable tags, scan on push), an ECS cluster, task definition and service with a deployment circuit breaker, IAM roles, a CloudWatch log group and the load balancer with its target group. Terraform created 29 resources (the ECR repository first, then 28 more in the full `terraform apply`), and `terraform destroy` removed them all afterwards because the load balancer and Fargate task bill by the hour.

The Django secret key is generated by Terraform and stored in AWS Secrets Manager, and ECS injects it into the container at start-up, so it never appears in the code or the task definition. Access is locked down in two layers: the load balancer accepts HTTP only from my IP, and the tasks accept port 8000 only from the load balancer. I confirmed that a direct request to the task's public IP times out.

I tested the API through the load balancer (create, list, filter, update, delete, pagination and validation errors), checked the target group showed healthy, stopped the running task to watch ECS start a replacement, and rolled out a second image tag with a rolling deployment. ECR scan on push reported no critical findings. The README documents the architecture, the results, the problems I fixed (a gunicorn `pkg_resources` crash, an ECR image index that could not be scanned, immutable tag conflicts) and the known limit that SQLite data is lost when a task is replaced, with RDS as the next step.

I then added a GitHub Actions CI/CD pipeline. On every pull request it runs the 36 tests and a Docker build, and `main` is protected so a change cannot merge until the `test` check passes. On merge to `main`, a second workflow reuses the test job, builds the image, pushes it to ECR tagged with the first 7 characters of the commit SHA (skipping the push if that tag already exists), renders a new ECS task definition and deploys it, then waits for the service to become stable. It signs in to AWS with OpenID Connect instead of stored access keys: a separate Terraform folder creates the OIDC provider and a least-privilege IAM role whose trust policy accepts only the `main` branch of this repository, and the role ARN is the only value kept in GitHub. A deliberately broken test turned the pull request red and blocked the merge. The first deploy failed with a `403 Forbidden` from ECR because the role lacked two read permissions; I added them to the policy and the run then deployed a new image to the running service. I did not test an automatic rollback of a failing deploy, and the stack was destroyed again after testing.

**Skills demonstrated:** GitHub Actions CI/CD, OpenID Connect (OIDC) federation to AWS, least-privilege IAM, branch protection, Terraform, Amazon ECS Fargate, Application Load Balancer, Amazon ECR, AWS Secrets Manager, IAM roles, security groups, VPC networking, CloudWatch Logs, Docker, rolling deployments, troubleshooting, cost control

## 💻 Software Projects

### 3. CRUD API (Django REST Framework)
**Repo:** [link](https://github.com/Bla-vk/Simple-CRUD-API)

A REST API for tracking items and the locations they are stored in, built with Django and Django REST Framework. It provides full Create, Read, Update and Delete endpoints under a versioned `/api/v1/` path, paginated list responses (20 per page) and filtering items by location.

I hardened and modernised it: the secret key, debug flag and allowed hosts now come from environment variables (the app refuses to start without a secret key), the missing DRF dependency was fixed, and list queries are ordered so pagination is stable. A suite of 36 automated tests covers every endpoint, validation errors, the unique location constraint, cascade deletes and pagination. The API is packaged in a Docker image served by gunicorn as a non-root user, and I checked it by running the container locally and creating and listing records through it, and later deployed it to AWS (project 2). The README documents setup, configuration, every endpoint with real `curl` examples, and the known limits.

**Skills demonstrated:** Python, Django, Django REST Framework, REST API design, automated testing, environment-based configuration and secrets hygiene, Docker, gunicorn, Git history review
